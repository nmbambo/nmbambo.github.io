· What it gives you

If you want to know where your organisation's numbers disagree, and which decisions rest on them,

A registry of meaning that checks itself: every term, metric and decision is recorded with an owner, and ordinary code, not a model, reports where definitions conflict and what would break if one changed.

I The problem

Finance, operations and the board hold different numbers for the same thing. Nobody can say which decisions were made on which meaning, or what a redefinition would invalidate. Reports and models are now written faster than anyone can read them.

II Approach

  1. Register terms, definitions, metrics and decisions with an owner, a unit and a grain. Adapters read dbt models, data dictionaries and Decision Language contracts, and say exactly what they could and could not read.
  2. Check with deterministic code: conflicting definitions, undefined or unowned terms, broken references, and decisions resting on a term whose meaning conflicts. Two names are one term only where an owner has said so, never because they look alike.
  3. Walk the graph. Select a term and see what depends on it, and what it depends on.
  4. Record each decision with a named owner and the conditions under which it would change, on a hash-chained ledger that can be verified without the platform.
  5. Let AI explain only what the code has already proved. Every reference an explanation makes is checked against what it was shown; an invented one is flagged, not kept.

III Structure

  1. KernelRegistry, coherence rules, dependency graph, ledger
  2. Adaptersdbt, data dictionary, Decision Language; each reports what was found, mapped, skipped or failed
  3. ExplanationClaude explains and answers questions by calling the kernel, scoped to one analysis
  4. WebRails and HTMX, Clerk sign-in, Postgres with row-level isolation

IV Craft and next

Python · Rails · HTMX · Postgres · Clerk · Claude

The kernel, adapters and ledger are built and tested. The web layer and database isolation are written but not yet run end to end, and the AI layer has not yet run against live models.

Delivery runs through the Ingqiqo factory: each change is specified, built in isolation, gated by tests, reviewed for security, code and meaning coherence, and approved by a named person, with every step recorded. The factory itself is tested but has not yet taken a live job. An effort estimator sits beside it and calls itself a prior until real outcomes replace it.
